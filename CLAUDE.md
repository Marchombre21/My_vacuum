## Project overview

Aspi is a home-built robot vacuum. Planned architecture:
- **Raspberry Pi** running ROS 2 (distro `lyrical`): SLAM mapping and path planning.
- **ESP32** (Rust, `no_std`): real-time sensors and actuators (IMU, wheel encoders, motors), sending data to the Pi.
- **Lidar**: Slamtec RPLIDAR **C1M1**, planned to plug **directly into the Pi over USB** (not through the ESP32).
- Development happens on two machines: the user's home PC (WSL2) and the school PC (an Ubuntu 26.04 VirtualBox VM, where no USB-serial device is visible so far; VirtualBox's Devices → USB menu might pass one through). The Pi is the deployment target. Setup steps (toolchains, USB access, RViz quirks) may differ between the two, so check which one you're on (`uname -r` contains `microsoft` on WSL2).

## Layout

- `esp32/` — ESP32 firmware, a Cargo project generated by `esp-generate` (crate and binary name `aspi_esp32`, renamed from `gyroscope` on 2026-10-07; not `esp32`, which is the name of the PAC crate esp-hal depends on; imported from the starter-kit tutorial repo `Marchombre21/gyroscope`). Uses esp-hal 1.1 + esp-rtos/embassy async. The code is in `src/bin/main.rs` (`src/lib.rs` is an empty `#![no_std]` stub). Code comments are in French.
  - It reads an MPU-6050/6500 IMU over I2C (exact model unknown: the firmware comments say 6500, the user thinks 6050; reading the `WHO_AM_I` register 0x75 tells: `0x68` = 6050, `0x70` = 6500) (SCL=GPIO18, SDA=GPIO23, address 0x68, 400 kHz). The OLED from the tutorial has been removed: the I2C bus is used directly (no `Mutex`/`I2cDevice`), with esp-hal's `*_async` methods (the methods without `_async` are the blocking ones).
  - Every 10 ms (100 Hz, paced by an `embassy_time::Ticker` so the period stays regular) it sends the raw data to the Pi over **UART2** (TX=GPIO17 → Pi RX/GPIO15, RX=GPIO16, common GND, default config 115200 baud). UART0 (the board's USB port) stays for flashing and `defmt` logs.
  - It also reads the two wheel encoders with the hardware pulse counter (PCNT): left A/B = GPIO25/26 (`unit0`), right A/B = GPIO32/33 (`unit1`), inputs with internal pull-up. `setup_quadrature()` configures a unit for ×4 quadrature counting (filter 800 = 10 µs). The hardware counter is only `i16`, so it is never cleared: each loop adds `now.wrapping_sub(last) as i32` to an `i32` total since startup (`wrapping_*` handles the i16 wrap-around). Whether the counter really wraps without limits set is **still to verify on hardware** (run a motor ~15 s, the total must keep growing).
  - Packet format (**25 bytes**, since 2026-10-07): header `0xAA 0x55` (0–1), then the 14 raw registers from 0x3B (2–15): accel X/Y/Z, temp, gyro X/Y/Z, each an `i16` **big-endian** (high byte first); then `left_total` (16–19) and `right_total` (20–23), each an `i32` big-endian (`to_be_bytes()`), total encoder counts since startup; then a 1-byte checksum (24): the sum of bytes 2–23 modulo 256 (`wrapping_add` over `&packet[2..24]` after filling, header not included). Python format: `'>7h2i'` (`>` = big-endian **and** standard sizes, no padding: `h` always 2 bytes, `i` always 4; `struct.calcsize('>7h2i')` = 22). The right wheel will count backwards when the robot goes forward (mirrored motors): fix the sign on the Pi side. On the Pi: find `0xAA 0x55`, read 23 bytes, check `sum(data) % 256 == checksum`; on mismatch, drop the packet and search for the next header. `Uart::write` may write fewer bytes than asked, so it is called in a loop until the whole packet is sent.
  - Conversion is done on the Pi side, not on the ESP32: accel `/16384` → g, `× 9.80665` → m/s². Gyro `/131` → °/s, `× π/180` → rad/s (ROS REP 103 units). Temp: `/340 + 36.53` → °C on an MPU-6050, `/333.87 + 21` on an MPU-6500. The gyro bias must be calibrated at startup (average while still). The ESP32 FPU handles only `f32`, so avoid `f64` on the firmware side.
  - `defmt` is not fully set up: `build.rs` doesn't add `-Tdefmt.x` and `.cargo/config.toml` has no `DEFMT_LOG`, so `info!` messages are probably compiled out.
- `ros2_ws/` — colcon workspace. `src/notes.md` is the user's project-wide notebook (explanations gathered during sessions); add new notes there rather than as long code comments. Each package has its own folder directly under `src/` (colcon stops descending once it finds a `package.xml`, so packages must never be nested).
  - `src/aspi_bringup/` — the user's own ament_cmake package (still an empty skeleton). Meant to hold the launch files and `.yaml` configs that start the whole robot (rplidar, slam_toolbox, Nav2, ESP32 bridge).
  - `src/aspi_imu_bridge/` — the user's own ament_python package (written by the user with explanations; IMU part tested on 2026-10-05 and wheel part on 2026-10-07, both with `tools/fake_esp32.py`, not yet with the real ESP32). The ESP32 bridge: it reads the 25-byte UART packets, does the conversion above and publishes `sensor_msgs/Imu` on `/imu/data_raw` (`_raw` = no orientation; `robot_localization` or `imu_filter_madgwick` will consume it later) and `sensor_msgs/JointState` on `/joint_states` (wheel angles). Depends on `python3-serial` (module `serial`). Code in the `aspi_imu_bridge/` module folder (no `src/` in ament_python): `imu_bridge.py` holds `main()` (entry point `imu_bridge` in `setup.py`, run with `ros2 run aspi_imu_bridge imu_bridge`), `imubridge.py` holds the `ImuBridge(Node)` class.
    - Parameters: `port` (default `/dev/serial0` on the Pi; `/dev/ttyUSB0` when testing on a PC with a 3.3 V USB-serial adapter), `frame_id` (default `imu_link`, used for the IMU message only), `ticks_per_rev` (default `1980`, an integer: the unverified guess 44 × 45; set it once the gear ratio is measured; launching with `ticks_per_rev:=1` makes `position` = counts × 2π, handy for the measurement). Baud rate is still hard-coded (115200).
    - A 5 ms timer calls `read_serial`: it appends `ser.read(ser.in_waiting)` (port opened with `timeout=0`, never blocks) to a `bytearray` buffer, then loops: find `0xAA 0x55`, drop bytes before it, wait if fewer than `PACKET_SIZE` (25) bytes, check the checksum over `buffer[2:PACKET_SIZE - 1]` (on mismatch drop only 1 byte and search again), decode the IMU part with `struct.unpack('>7h', buffer[2:16])`, convert, then remove the 25 bytes.
    - Startup calibration: the first 200 packets (~2 s, robot still because nothing commands the motors yet) are stored in `calib_samples` and not published. `finish_calibration()` then computes the gyro bias (`statistics.fmean`, subtracted from every gyro reading afterwards) and the per-axis variance of accel and gyro (`statistics.pvariance`, on converted values). No bias is removed from the accel (it measures gravity). `gyro_bias is None` means "still calibrating".
    - Covariances: `orientation_covariance[0] = -1` (no orientation). Angular velocity / linear acceleration covariances: the variances go on the diagonal (indices 0, 4, 8), the rest stays 0. Values measured at rest will likely need to be raised later (motor vibrations) when tuning `robot_localization`.
    - Temperature is converted (MPU-6050 formula, pending the `WHO_AM_I` check) but not published: `sensor_msgs/Imu` has no field for it (`sensor_msgs/Temperature` exists if needed later).
    - The user's learning notes (e.g. the `'>7h'` explanation) live in `ros2_ws/src/notes.md`, not in code comments; `imubridge.py` only points to them (`# Voir notes`).
    - Wheels: `struct.unpack('>2i', buffer[16:24])` (before the `del`), then `right = -right` so that both wheels count positive when the robot goes forward (assumed: the mirrored right motor counts backwards; **to check on the real robot**: push it forward, both positions must grow; otherwise invert the other wheel or swap that wheel's A/B wires; maybe `invert_left`/`invert_right` parameters later). One `JointState` per packet for both wheels: `name = ['left_wheel_joint', 'right_wheel_joint']` (must match the future URDF joint names), `position` = `total / ticks_per_rev * 2π` (radians since startup), `velocity` and `effort` left empty (allowed by the message: each list is either empty or as long as `name`), `header.frame_id` empty. The IMU and JointState messages share one timestamp (`clk_now`). Like the IMU, nothing is published during calibration; no wheel count is lost since the ESP32 sends totals.
    - Odometry (`nav_msgs/Odometry` on `/odom`) is deliberately **not** published yet: it needs the measured gear ratio, the wheel spacing (unknown until mounted) and the integration math. It will be computed from `/joint_states` later (separate node or inside the bridge).
    - Still to do: test with the real ESP32 (UART wiring + Pi setup below).
    - Pi side still to set up: enable the hardware UART on GPIO14/15, disable the serial console (Ubuntu: `enable_uart=1` in `/boot/firmware/config.txt`, remove `console=serial0,...` from `cmdline.txt`), add the user to the `dialout` group.
  - `src/rplidar/` — Slamtec's `rplidar_ros` (branch `ros2`), package name `rplidar_ros`. Its files are tracked directly by the main git repo (no nested repo, no submodule). Its root `CMakeLists.txt` has local changes (`ament_target_dependencies` → `target_link_libraries`).
- `tools/` (at the repo root, outside the colcon workspace, so colcon never sees it) — dev helpers that are not ROS packages.
  - `fake_esp32.py` (written by the user) — plays the ESP32 for testing `aspi_imu_bridge` without hardware: sends valid 25-byte packets every 10 ms on the serial port given as argument (accel Z = 16384 = 1 g, gyro biases 120/50/90 raw, ±20 random noise on each value; encoder totals: left +5 and right −5 per packet, like a mirrored right wheel). Keep its packet format in sync with the firmware and the bridge.
- Nav2 and slam_toolbox are meant to be installed with `apt`, not added as source to the workspace.

## Next steps (decided on 2026-10-05)

Wheel encoders, to be sent to the Pi:
- **Design**: one bridge node only, since two processes can't read the same serial port (each byte read is gone for the other). The bridge reads and decodes the packet, then publishes one topic per data kind (`/imu/data_raw` and `/joint_states`; `/odom` later). Later it will also send motor commands to the ESP32 (UART RX line) and can be renamed (e.g. `aspi_esp32_bridge`).
- **Packet**: one packet, extended. The encoder counts are appended after the 14 IMU bytes (same 100 Hz loop). Send the **total count since startup** as an `i32` (not the count since the last packet), so a dropped packet loses nothing. Update the size, the `struct` format and `tools/fake_esp32.py` together.
- **ESP32**: read the encoders with the hardware pulse counter (PCNT, esp-hal), in the existing loop (no extra task or interrupt).

Order:
1. [ ] Identify the encoder hardware. Partly done on 2026-10-06:
   - Motors: DC gear motors with a magnetic Hall encoder and 65 mm wheels (generic "smart car" kit, likely JGA25-370 style). Wires: red/white = motor +/−, blue/black = encoder power (3.3–5 V; **power it at 3.3 V** so the signals stay safe for the ESP32 GPIOs), yellow/green = channels A/B.
   - Encoder: **two-channel A/B quadrature**, 11 pulses per **motor** turn → 44 counts per motor turn when PCNT counts every edge of both channels (×4). Direction is handled by PCNT.
   - Variant bought: **12 V, 130 rpm** (no load). ≈ 0.44 m/s no load, ≈ 0.3–0.35 m/s expected on the robot (L298N drop + load).
   - Counts per wheel turn = 44 × gear ratio. **Gear ratio to be measured**: often ~1:45 for this variant (unverified guess → ~1980 counts per wheel turn, ~0.1 mm per count). An online "planetary 99:1" result is probably another product (this kit looks like a spur-gear JGA25-370). Measure in step 3: turn the wheel 10 full turns by hand, ratio = count ÷ 440. Wheel circumference = π × 65 ≈ 204 mm.
   - Still to gather: gear ratio (measurement above), distance between the wheels (center to center, once mounted).
   - Power: a 12 V or 3S lithium battery (11.1–12.6 V) works with the 78M05 jumper left on. Do **not** power the Pi from the L298N 5 V output (~0.5 A max, the Pi needs ≥ 3 A): use a separate 12 V → 5 V buck converter (≥ 3 A) on the battery.
   - Motor driver: L298N dual H-bridge module (Zua-YXJ-036, 2 bought; one module drives both wheels) with an on-board 78M05 5 V regulator. See `notes.md` for wiring and the regulator jumper. ESP32 3.3 V logic is enough for its inputs. Motor control (PWM, LEDC/MCPWM on the ESP32) is not planned yet.

## Build & flash (ESP32)

- Needs the Xtensa Rust toolchain (`rust-toolchain.toml` → channel `esp`, installed with `espup`) and `espflash`. Each dev machine needs its own install: `rustup`, then `cargo install espup --locked && espup install`, then `cargo install espflash --locked`, and `source ~/export-esp.sh` in the shell. Do **not** use Espressif's EIM / ESP-IDF installer (that is for C development; it was installed by mistake on the home PC and removed on 2026-10-07). Home PC (WSL2, reinstalled): rustup, espup, the `esp` toolchain and espflash reinstalled on 2026-10-07, plus `socat`, and the ROS workspace rebuilt. On WSL2, flashing also needs the USB device passed through with `usbipd` from Windows.
- From `esp32/`: `cargo build --release`, `cargo run --release` (flashes with `espflash flash --monitor --chip esp32`). The target `xtensa-esp32-none-elf` and `build-std` are set in `.cargo/config.toml`.

## Build & run (ROS 2)

- Build everything from `ros2_ws/`:
  ```bash
  cd ros2_ws
  source /opt/ros/lyrical/setup.zsh
  colcon build --symlink-install
  source install/setup.zsh
  ros2 launch rplidar_ros view_rplidar_c1_launch.py   # C1: 460800 baud, /dev/ttyUSB0 by default
  ```
- `src/rplidar/` still contains old `build/`, `install/` and `log/` folders from when it was built on its own. They are git-ignored and no longer used.
- On WSL2 (home PC), RViz needs `export QT_QPA_PLATFORM=xcb`. Otherwise Qt picks Wayland while Ogre uses GLX, and you get "Invalid parentWindowHandle". If the 3D view stays black: `export LIBGL_ALWAYS_SOFTWARE=1`.
- `ament_target_dependencies` is deprecated in this distro. Use `target_link_libraries` with the target names: `rclcpp::rclcpp`, `${<msg_pkg>_TARGETS}`.
- Testing the IMU bridge without hardware (works on the school VM):
  ```bash
  socat -d -d pty,raw,echo=0 pty,raw,echo=0          # terminal 1: virtual serial cable, prints two /dev/pts/N
  python3 tools/fake_esp32.py /dev/pts/X             # terminal 2: first port
  ros2 run aspi_imu_bridge imu_bridge --ros-args -p port:=/dev/pts/Y   # terminal 3 (sourced): second port
  ros2 topic echo /imu/data_raw sensor_msgs/msg/Imu --once             # terminal 4 (sourced)
  ```
  Each new terminal must source `/opt/ros/lyrical/setup.zsh` and `install/setup.zsh` (zsh, not bash), otherwise `ros2 run` says the package is not found. Giving the type to `topic echo` lets it wait before the bridge starts (without it: "Could not determine the type"); started first, it stays silent ~2 s (calibration) then prints one message. Expected with the fake ESP32: `linear_acceleration.z` ≈ 9.81, x/y ≈ 0 (±0.01), `angular_velocity` ≈ 0 (±0.003, biases removed), covariance diagonals ≈ 2.5e-06 (gyro) and ≈ 5e-05 (accel). Verified on 2026-10-05. `ros2 topic echo /joint_states sensor_msgs/msg/JointState --once`: both positions equal and growing by ≈ 0.016 rad per packet (5 / 1980 × 2π), ~99 Hz with `ros2 topic hz /joint_states`. Verified on 2026-10-07. (`topic echo` has no `--times` option in this distro; use `--once`.)
- No automated tests exist yet. `aspi_bringup` only has the default `ament_lint_auto` setup and `aspi_imu_bridge` the default linters (flake8, pep257, mypy, copyright, xmllint), all run with `colcon test`.
