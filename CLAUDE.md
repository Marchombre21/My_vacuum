## Project overview

Aspi is a home-built robot vacuum. Planned architecture:
- **Raspberry Pi** running ROS 2 (distro `lyrical`): SLAM mapping and path planning.
- **ESP32** (Rust, `no_std`): real-time sensors and actuators (IMU, wheel encoders, motors), sending data to the Pi.
- **Lidar**: Slamtec RPLIDAR **C1M1**, planned to plug **directly into the Pi over USB** (not through the ESP32).
- Development happens on two machines: the user's home PC (WSL2) and the school PC (an Ubuntu 26.04 VM). The Pi is the deployment target. Setup steps (toolchains, USB access, RViz quirks) may differ between the two, so check which one you're on (`uname -r` contains `microsoft` on WSL2).

## Layout

- `esp32/` — ESP32 firmware, a Cargo project generated by `esp-generate` (crate name `gyroscope`, imported from the starter-kit tutorial repo `Marchombre21/gyroscope`). Uses esp-hal 1.1 + esp-rtos/embassy async. The code is in `src/bin/main.rs` (`src/lib.rs` is an empty `#![no_std]` stub). Code comments are in French.
  - It reads an MPU-6500 IMU over I2C (SCL=GPIO18, SDA=GPIO23, address 0x68, 400 kHz). The OLED from the tutorial has been removed: the I2C bus is used directly (no `Mutex`/`I2cDevice`), with esp-hal's `*_async` methods (the methods without `_async` are the blocking ones).
  - Every 10 ms (100 Hz, paced by an `embassy_time::Ticker` so the period stays regular) it sends the raw data to the Pi over **UART2** (TX=GPIO17 → Pi RX/GPIO15, RX=GPIO16, common GND, default config 115200 baud). UART0 (the board's USB port) stays for flashing and `defmt` logs.
  - Packet format (17 bytes): header `0xAA 0x55`, then the 14 raw registers from 0x3B: accel X/Y/Z, temp, gyro X/Y/Z, each an `i16` **big-endian** (high byte first), then a 1-byte checksum: the sum of the 14 data bytes modulo 256 (`wrapping_add`, header not included). On the Pi: find `0xAA 0x55`, read 15 bytes, check `sum(data) % 256 == checksum`; on mismatch, drop the packet and search for the next header. `Uart::write` may write fewer bytes than asked, so it is called in a loop until the whole packet is sent.
  - Conversion is done on the Pi side, not on the ESP32: accel `/16384` → g, `× 9.80665` → m/s². Gyro `/131` → °/s, `× π/180` → rad/s (ROS REP 103 units). Temp (MPU-6500) `/333.87 + 21` → °C. The gyro bias must be calibrated at startup (average while still). The ESP32 FPU handles only `f32`, so avoid `f64` on the firmware side.
  - `defmt` is not fully set up: `build.rs` doesn't add `-Tdefmt.x` and `.cargo/config.toml` has no `DEFMT_LOG`, so `info!` messages are probably compiled out.
- `ros2_ws/` — colcon workspace. Each package has its own folder directly under `src/` (colcon stops descending once it finds a `package.xml`, so packages must never be nested).
  - `src/aspi_bringup/` — the user's own ament_cmake package (still an empty skeleton). Meant to hold the launch files and `.yaml` configs that start the whole robot (rplidar, slam_toolbox, Nav2, ESP32 bridge).
  - `src/aspi_imu_bridge/` — the user's own ament_python package (**in progress**, written by the user with explanations; untracked in git so far). The ESP32 bridge: it reads the UART packets, does the conversion above and publishes `sensor_msgs/Imu` on `/imu/data_raw` (`_raw` = no orientation; `robot_localization` or `imu_filter_madgwick` will consume it later). Depends on `python3-serial` (module `serial`). Code in the `aspi_imu_bridge/` module folder (no `src/` in ament_python): `imu_bridge.py` holds `main()` (entry point `imu_bridge` in `setup.py`, run with `ros2 run aspi_imu_bridge imu_bridge`), `imubridge.py` holds the `ImuBridge(Node)` class.
    - Parameters: `port` (default `/dev/serial0` on the Pi; `/dev/ttyUSB0` when testing on a PC with a 3.3 V USB-serial adapter), `frame_id` (default `imu_link`). Baud rate is still hard-coded (115200).
    - A 5 ms timer calls `read_serial`: it appends `ser.read(ser.in_waiting)` (port opened with `timeout=0`, never blocks) to a `bytearray` buffer, then loops: find `0xAA 0x55`, drop bytes before it, wait if fewer than 17 bytes, check the checksum (on mismatch drop only 1 byte and search again), decode with `struct.unpack('>7h', buffer[2:16])`, convert, then remove the 17 bytes.
    - Startup calibration: the first 200 packets (~2 s, robot still because nothing commands the motors yet) are stored in `calib_samples` and not published. `finish_calibration()` then computes the gyro bias (`statistics.fmean`, subtracted from every gyro reading afterwards) and the per-axis variance of accel and gyro (`statistics.pvariance`, on converted values). No bias is removed from the accel (it measures gravity). `gyro_bias is None` means "still calibrating".
    - Covariances: `orientation_covariance[0] = -1` (no orientation). Angular velocity / linear acceleration covariances: the variances go on the diagonal (indices 0, 4, 8), the rest stays 0. Values measured at rest will likely need to be raised later (motor vibrations) when tuning `robot_localization`.
    - Still to do: fill `angular_velocity` / `linear_acceleration` and their covariances, subtract the gyro bias, `publish`. Known bugs left on 2026-10-03: checksum line uses Rust slice syntax `[2..PACKET_SIZE - 1]` (must be `[2:PACKET_SIZE - 1]`); the calibration branch lacks a `continue`; the normal path never removes the packet from the buffer (infinite loop); temperature uses the MPU-6050 formula; unused `qos_profile_rosout_default` import; cleanup in `main()` is skipped on Ctrl+C (needs `try/finally`).
    - Pi side still to set up: enable the hardware UART on GPIO14/15, disable the serial console (Ubuntu: `enable_uart=1` in `/boot/firmware/config.txt`, remove `console=serial0,...` from `cmdline.txt`), add the user to the `dialout` group.
  - `src/rplidar/` — Slamtec's `rplidar_ros` (branch `ros2`), package name `rplidar_ros`. Its files are tracked directly by the main git repo (no nested repo, no submodule). Its root `CMakeLists.txt` has local changes (`ament_target_dependencies` → `target_link_libraries`).
- Nav2 and slam_toolbox are meant to be installed with `apt`, not added as source to the workspace.

## Build & flash (ESP32)

- Needs the Xtensa Rust toolchain (`rust-toolchain.toml` → channel `esp`, installed with `espup`) and `espflash`. Each dev machine needs its own install: `rustup`, then `cargo install espup --locked && espup install`, then `cargo install espflash --locked`, and `source ~/export-esp.sh` in the shell. On WSL2, flashing also needs the USB device passed through with `usbipd` from Windows.
- From `esp32/`: `cargo build --release`, `cargo run --release` (flashes with `espflash flash --monitor --chip esp32`). The target `xtensa-esp32-none-elf` and `build-std` are set in `.cargo/config.toml`.

## Build & run (ROS 2)

- Build everything from `ros2_ws/`:
  ```bash
  cd ros2_ws
  source /opt/ros/lyrical/setup.zsh
  colcon build --symlink-install
  source install/setup.zsh
  ros2 launch rplidar_ros view_rplidar_c1_launch.py   # C1: 460800 baud, /dev/ttyUSB0 by default
  ```
- `src/rplidar/` still contains old `build/`, `install/` and `log/` folders from when it was built on its own. They are git-ignored and no longer used.
- On WSL2 (home PC), RViz needs `export QT_QPA_PLATFORM=xcb`. Otherwise Qt picks Wayland while Ogre uses GLX, and you get "Invalid parentWindowHandle". If the 3D view stays black: `export LIBGL_ALWAYS_SOFTWARE=1`.
- `ament_target_dependencies` is deprecated in this distro. Use `target_link_libraries` with the target names: `rclcpp::rclcpp`, `${<msg_pkg>_TARGETS}`.
- No tests exist yet. `aspi_bringup` only has the default `ament_lint_auto` setup and `aspi_imu_bridge` the default linters (flake8, pep257, mypy, copyright, xmllint), all run with `colcon test`.
